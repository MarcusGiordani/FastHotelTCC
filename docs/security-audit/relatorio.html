4. Pontos Fortes

Proteções e boas práticas efetivamente verificadas no código — evidência de que a auditoria percorreu o sistema além de procurar apenas problemas.

  • OK Senhas com hash bcrypt: userController.js (createUser, changePassword) usa bcrypt.genSalt(10) + bcrypt.hash; nenhuma senha em texto puro é gravada ou retornada pela API.
  • OK Senha nunca retornada: todos os SELECT/RETURNING de usuário (createUser, getAllUsers, getUserById, updateUser, loginUser) listam colunas explicitamente e nunca incluem senha no JSON de resposta.
  • OK Troca de senha corretamente escopada ao próprio usuário: changePassword (userController.js:172-204) usa req.user.id (do token) para localizar o registro, nunca um id vindo da URL/body — impossível alterar a senha de outra conta por esse endpoint.
  • OK Reservas isolam corretamente por usuário: bookingController.getAllBookings e getBookingById (linhas 111-192) filtram por usuario_id = req.user.id quando o solicitante não é admin; updateBooking/deleteBooking verificam tipo_usuario antes de alterar/excluir, redundante com a proteção de rota.
  • OK Relatórios/analytics corretamente restritos: todas as 8 rotas de reportRoutes.js exigem auth + authorize(['admin','recepcionista']), incluindo o dashboard e os relatórios agregados.
  • OK SQL parametrizado em 100% das queries de aplicação: nenhuma concatenação de entrada do usuário em string SQL foi encontrada em nenhum controller — todas usam $1, $2, ....
  • OK CORS restrito: fasthotel-api/app.js configura origin: process.env.FRONTEND_URL (não usa *).
  • OK Nenhum segredo real no repositório: busca completa no código, configs, CI e histórico do Git não encontrou chave, token ou senha real — apenas placeholders e credenciais de teste (ver seção 7).
  • OK Isolamento do banco de testes: os testes de integração e E2E têm trava explícita que recusa executar se PGDATABASE não for fasthotel_test (tests/integration/setup.env.js), nunca tocando o banco de desenvolvimento fasthotel_db.
  • OK Sem sink de HTML perigoso no frontend: nenhum uso de dangerouslySetInnerHTML, innerHTML, eval ou new Function em toda a árvore fasthotel-app/src.
  • OK JWT com expiração curta: tokens assinados com expiresIn: '1h' (userController.js:149), reduzindo a janela de uso de um token roubado.

F01 — Autocadastro público permite criar conta administradora

Categoria: 2 — Permissão definida no navegador  |  Severidade: Crítica  |  Rota: POST /api/usuarios

Arquivos: fasthotel-api/routes/userRoutes.js:9-18; fasthotel-app/src/pages/UserRegistration/index.tsx:22,41,81-90; fasthotel-app/src/routes/index.tsx:24

);
// fasthotel-app/src/pages/UserRegistration/index.tsx:87-89
<option value="recepcionista">Recepcionista</option>
<option value="admin">Administrador</option>

Por que é explorável: a rota de cadastro não possui middleware de autenticação e aceita o campo tipo_usuario diretamente do corpo da requisição; a tela pública /register (fora de PrivateRoute) oferece livremente a opção "Administrador" no formulário.

Impacto: comprometimento total do sistema — qualquer pessoa na internet obtém uma conta admin sem qualquer credencial prévia.

Condições de exploração: nenhuma. Não exige autenticação, não exige conhecimento prévio do sistema.

Evidência: POST /api/usuarios com corpo {"nome":"x","email":"x@x.com","senha":"123456","tipo_usuario":"admin"} retorna 201 e cria a conta como administrador, sem qualquer cabeçalho de autenticação.

F02 — Auto-promoção a administrador via PUT /api/usuarios/:id

Categoria: 3 — IDOR / Escalonamento de privilégio  |  Severidade: Crítica  |  Rota: PUT /api/usuarios/:id

Arquivos: fasthotel-api/routes/userRoutes.js:22; fasthotel-api/controllers/userController.js:73-96

// fasthotel-api/routes/userRoutes.js:22
router.put('/:id', auth, authorize(['admin', 'recepcionista', 'cliente']), userController.updateUser);
// authorize() lista TODOS os papéis válidos -> equivale a não restringir nada

// fasthotel-api/controllers/userController.js:73-81
const updateUser = async (req, res) => {
    const { id } = req.params;
    const { nome, email, tipo_usuario } = req.body;
    const updatedUser = await pool.query(
        'UPDATE usuarios SET nome = $1, email = $2, tipo_usuario = $3 WHERE id = $4 RETURNING id, nome, email, tipo_usuario',
        [nome, email, tipo_usuario, id]     // <- "id" da URL, sem comparar com req.user.id
    );

Por que é explorável: o handler nunca compara req.params.id com req.user.id, e grava qualquer valor de tipo_usuario enviado no corpo, sem restringir esse campo a quem já é admin.

Impacto: qualquer conta cliente chama PUT /api/usuarios/<próprio id> com {"tipo_usuario":"admin"} e se torna administrador; o mesmo endpoint permite alterar e-mail/nome/papel de qualquer outro usuário, inclusive rebaixar administradores existentes.

Condições de exploração: exige apenas login válido como qualquer papel (inclusive o de menor privilégio, cliente).

Evidência: com token JWT de um usuário cliente, PUT /api/usuarios/<id do próprio token> com {"tipo_usuario":"admin"} retorna 200 e o campo tipo_usuario da resposta passa a ser "admin".

F03 — Exposição de dados de qualquer usuário via GET /api/usuarios/:id

Categoria: 3 — IDOR  |  Severidade: Média  |  Rota: GET /api/usuarios/:id

Arquivos: fasthotel-api/routes/userRoutes.js:21; fasthotel-api/controllers/userController.js:58-70

// fasthotel-api/controllers/userController.js:58-61

Por que é explorável: a consulta usa apenas o id da URL; a rota permite os três papéis válidos (admin, recepcionista, cliente), tornando a checagem de authorize inócua.

7. Categorias Sem Vulnerabilidade Verificável

Categoria 4 — Chaves expostas / segredos

Analisada — sem achado

Foi feita busca no código-fonte completo (backend e frontend), em .env.example, .env.test.example, no workflow de CI (.github/workflows/ci.yml) e em todo o histórico do Git (git log --all -p) por padrões de chave de API, JWT secret, senha, token de webhook e credenciais em URLs de conexão. Os únicos valores encontrados foram placeholders explícitos (troque-por-sua-senha-local, troque-por-uma-chave-longa-e-aleatoria, sua-senha-local) e uma credencial de teste sem valor sensível (JWT_SECRET = [REDACTED], valor fixo usado apenas nos testes de integração/E2E locais, nunca em produção). O .env e o .env.test reais (que contêm a senha do PostgreSQL local) nunca foram commitados — confirmado tanto pelo .gitignore atual quanto pela ausência desses arquivos em todo o histórico. O CI usa exclusivamente credenciais de teste definidas dentro do próprio arquivo de workflow (postgres/postgres no container do PostgreSQL, JWT_SECRET = [REDACTED]). Não foi encontrado achado verificável nesta categoria.

Categoria 5 — Inputs sem tratamento / XSS

Analisada — sem achado

Foi feita busca por dangerouslySetInnerHTML, innerHTML, document.write, eval, new Function, javascript: e insertAdjacentHTML em toda a árvore fasthotel-app/src — nenhuma ocorrência. Nenhum componente insere HTML/Markdown vindo do usuário; todo conteúdo dinâmico (incluindo mensagens de chat em ChatOnline/index.tsx, que é o dado mais "livre" gerado por usuário no sistema) é renderizado via interpolação JSX padrão ({msg.conteudo}), que o React escapa automaticamente. Nenhum href/src do projeto é construído a partir de entrada do usuário. No backend, não existe geração de e-mail, template HTML ou qualquer resposta que misture HTML com dados do usuário — a API só retorna JSON. Não foi encontrado achado verificável nesta categoria.

Categoria 1 — Banco sem tranca (isolamento de dados)

Analisada — mecanismo identificado

O FastHotel não é multi-tenant; o mecanismo de isolamento identificado é um filtro manual por usuario_id, aplicado quando o solicitante não é admin. Esse mecanismo está corretamente implementado em bookingController.getAllBookings e getBookingById (fasthotel-api/controllers/bookingController.js:111-192) — ver seção 4, Pontos Fortes. Entretanto, o mesmo filtro não foi propagado para as tabelas dependentes de reservas: pagamentos e consumos. Essa lacuna já está documentada tecnicamente como F07 e F08 (Categoria 3) na seção 6 — não há, portanto, um achado adicional e distinto de Categoria 1 além do que já foi reportado nesses dois IDs.

8. Recomendações

Priorização baseada exclusivamente nos achados reais desta auditoria — nenhuma prioridade foi criada para achados inexistentes.

P1 — Urgente Corrigir antes de qualquer outra atividade

  • F01 — Exigir autenticação/privilégio de admin para criar contas com tipo_usuario diferente de cliente; a rota pública de cadastro deve sempre forçar cliente.
  • F02 — Em updateUser, comparar req.params.id com req.user.id e proibir a alteração de tipo_usuario por quem não é admin.
  • F04 — Adicionar auth + authorize(['admin','recepcionista']) nas rotas de escrita de roomRoutes.js.
  • F09 — Restringir POST /api/pagamentos a admin/recepcionista.

P2 — Alto Corrigir na sequência, mesmo padrão de causa raiz

  • F05 — Adicionar authorize(['admin','recepcionista']) em guestRoutes.js.
  • F06 — Adicionar authorize(['admin','recepcionista']) nas rotas de escrita de serviceRoutes.js.
  • F07 — Adicionar authorize nas rotas de escrita de consumptionRoutes.js e filtrar leitura por propriedade da reserva.
  • F08 — Filtrar getAllPayments/getPaymentById por reservas.usuario_id = req.user.id quando o papel não for admin/recepcionista.

P3 — Moderado

  • F03 — Restringir GET /api/usuarios/:id de terceiros a admin/recepcionista; permitir a qualquer usuário apenas o próprio registro.

O detalhamento de como implementar e testar cada correção está em docs/security-audit/plano-correcao-vulnerabilidades.md. Nenhuma correção foi aplicada ao código nesta auditoria.

# [Segurança] Qualquer usuário autenticado pode se autopromover a administrador
  ou alterar dados de qualquer conta (F02, F03)

Labels sugeridas:
security
severity:critical

## Descrição
PUT /api/usuarios/:id não verifica se o "id" da URL corresponde ao usuário
autenticado, e grava qualquer "tipo_usuario" enviado no corpo. GET /api/usuarios/:id
retorna dados (nome, e-mail, papel) de qualquer usuário para qualquer autenticado.

## Por que é explorável
authorize(['admin','recepcionista','cliente']) inclui todos os papéis válidos,
equivalendo a nenhuma restrição. O controller nunca compara req.params.id com
req.user.id (fasthotel-api/controllers/userController.js:58-70,73-96).

## Evidência

fasthotel-api/routes/userRoutes.js:21,22
fasthotel-api/controllers/userController.js:58-70 (getUserById)
fasthotel-api/controllers/userController.js:73-96 (updateUser)

```text
const updatedUser = await pool.query(
    'UPDATE usuarios SET nome = $1, email = $2, tipo_usuario = $3 WHERE id = $4 ...',
    [nome, email, tipo_usuario, id]
);
```

## Impacto
Qualquer conta "cliente" pode se tornar "admin" chamando o próprio ID, ou alterar/
consultar dados de qualquer outra conta.

## Sugestão de correção
Comparar req.params.id com req.user.id; só permitir alterar/consultar dados de
terceiros e o campo tipo_usuario quando req.user.tipo_usuario === 'admin'.

## Critérios de aceite
- Um usuário não-admin não consegue alterar tipo_usuario (nem o próprio, nem de outros)
- Um usuário não-admin só consulta/altera o próprio registro
- Teste de integração cobre autopromoção, alteração de terceiro e leitura de terceiro

# [Segurança] Rotas de gestão de quartos sem nenhuma autenticação (F04)

Labels sugeridas:
security
severity:critical

## Descrição
Todas as rotas de /api/quartos (criar, listar, obter, atualizar, excluir) estão

## Por que é explorável
fasthotel-api/routes/roomRoutes.js:7-11 não importa nem usa "auth"/"authorize"

router.post('/', roomController.createRoom);

# [Segurança] Rotas de Hóspedes, Serviços e Consumos sem controle de acesso (F05, F06, F07)

Labels sugeridas:
security
severity:high

## Descrição
As rotas de /api/hospedes, /api/servicos e /api/consumos exigem apenas login
válido ("auth"), sem restringir por papel ("authorize") nem verificar
propriedade do recurso. Qualquer conta "cliente" pode ler/alterar/excluir
hóspedes (incluindo CPF/RG), o catálogo de serviços/preços, e consumos de
QUALQUER reserva.

## Por que é explorável
- fasthotel-api/routes/guestRoutes.js:7-11 (só auth)
- fasthotel-api/routes/serviceRoutes.js:8-12 (só auth)
- fasthotel-api/routes/consumptionRoutes.js:8-12 (só auth)
Nenhum dos três controllers valida req.user.tipo_usuario nem propriedade da reserva.
Confirmado também no frontend: fasthotel-app/src/pages/Guests/index.tsx:218-229
renderiza os botões de editar/excluir para qualquer usuário logado, e
fasthotel-app/src/components/PrivateRoute/index.tsx:8-11 só verifica o token,
nunca o papel.

## Evidência

fasthotel-api/controllers/guestController.js:96-108,111-142,145-205
fasthotel-api/controllers/serviceController.js:5-21,50-69,72-84
fasthotel-api/controllers/consumptionController.js:5-34,105-150,153-165

## Impacto
Exposição/alteração de PII de hóspedes; tampering de preços; fraude/sabotagem
de consumos em reservas de terceiros.

## Sugestão de correção
Adicionar authorize(['admin','recepcionista']) nas rotas de escrita das três
entidades; em Consumos, filtrar leitura por propriedade da reserva
(reservas.usuario_id = req.user.id) para papéis não-admin, no mesmo padrão já
usado em bookingController.getAllBookings.

## Critérios de aceite
- cliente autenticado recebe 403 ao criar/alterar/excluir hóspede, serviço ou consumo
- cliente autenticado, ao listar consumos, só vê os das próprias reservas
- admin/recepcionista continuam funcionando normalmente

# [Segurança] Pagamentos sem controle de acesso e criação fraudulenta com status "aprovado" (F08, F09)

Labels sugeridas:
security
severity:critical

## Descrição
GET /api/pagamentos e GET /api/pagamentos/:id retornam dados financeiros de
qualquer reserva para qualquer usuário autenticado. POST /api/pagamentos aceita
qualquer reserva_id e grava status_pagamento='aprovado' por padrão quando o
campo não é enviado, sem qualquer confirmação de pagamento real.

## Por que é explorável
fasthotel-api/routes/paymentRoutes.js:8,9,14 só exigem "auth" nessas três rotas.
O filtro manual por usuario_id, usado corretamente em bookingController, não foi
propagado para pagamentos.

## Evidência

fasthotel-api/controllers/paymentController.js:5-26 (createPayment)
fasthotel-api/controllers/paymentController.js:29-74 (getAllPayments)
fasthotel-api/controllers/paymentController.js:77-114 (getPaymentById)

```text
[reserva_id, valor_pago, metodo_pagamento, status_pagamento || 'aprovado']
```

## Impacto
Exposição de histórico financeiro de terceiros; fraude - qualquer "cliente"
pode marcar a própria (ou outra) reserva como paga sem pagar nada.

## Sugestão de correção
Restringir POST /api/pagamentos a admin/recepcionista. Filtrar GET (lista e por
ID) por reservas.usuario_id = req.user.id quando o papel não for admin/recepcionista.

## Critérios de aceite
- cliente autenticado recebe 403 ao tentar criar um pagamento
- cliente autenticado só vê pagamentos das próprias reservas
- admin/recepcionista continuam funcionando normalmente
